# 产品改进：第一批交付与后续验收

本轮保留 king / AI 同字号品牌底板、暖白与橙色视觉。目标是让已发布数据可信、当前目录可用、收藏与选型流程可靠。

## 本轮实现

| 改进 | 实际行为 | 验证边界 |
| --- | --- | --- |
| 分享图中文 | 明确 CJK 字体，真实字形预检；缺字阻断发布 | 本机 PNG 与 Ubuntu CI 分别验证；不承诺跨字体版本相同字节 |
| 累计榜完整性 | 同查询分页查重、数量核对、完整重试一次；失败保留旧版 | 不把 GitHub Search 当作事务快照，仍以采集时可观测范围为准 |
| 收藏与同步 | 未知先重查，单个登录意图确认，部分成功保留，失效停批次，防旧账号响应 | 模拟账号回归；真实 Worker/OAuth 需要单独部署验收 |
| 当前项目目录 | /board/ 使用当前候选 catalog；/discover/ 静态100项分页；含待分类兜底 | 不等于 GitHub 全量；项目方向/形态/场景依赖已发布分类 |
| 历史入口 | 事件分类移到 /board/archive/；周期榜明确历史或积累状态 | 旧链接保留，缺窗口不补造 |
| 项目对比 | 按稳定 ID 刷新最多4个本站详情，显示来源日期/创建/提交日期，失败保留并标旧值 | 每项观察日期可能不同；不是实时 GitHub 查询 |
| 相似项目 | 共同用途优先于大类，显示现有分类依据及数据日期 | 不推断功能等价、许可或质量 |
| 数据维护 | 删除种子后解除固定，改名保留稳定ID/历史；迁移只比较前自然日 | 不重写既有线上快照 |
| 内容补全顺序 | 最新日榜Top100优先，再处理当前候选中的既有补全来源 | 保留旧版coverage/hash契约；首次只在目录出现的项目可通过显式1.1版本迁移接入 |
| 本地预览 | SVG/WebP提供正确类型，并检查logo实际加载 | 预览通过不等于生产已发布 |

## 连续观察与扩大收录：源码已实现，生产待验收

已拆分最多5,000项的发现目录与最多2,000项的每日观察池；观察保护、容量换入限制、同日重放和覆盖说明已实现。新采集才启用，旧固定数据仍可部署。不能把本次升级称为GitHub全量收录或连续窗口已恢复。

- 为稳定仓库 ID 记录观察开始日、保护截止日和最近有效快照；正在形成7/30日窗口的项目优先保留。
- 每日接纳新观察项目设容量与换入上限；新发现可先进入目录，不因进入发现结果就驱逐正在观察的项目。
- 迁移前模拟现有快照，比较换入率、可比数、连续窗口覆盖及API预算；不足容量时明确排队，不虚构连续数据。
- 已实现补全1.1显式迁移：隔离副本离线协调缓存与coverage、验证后形成新数据提交，再部署固定版本；旧deploy_existing及历史迁移入口继续接受1.0。生产迁移与在线补全尚未执行。

验收：至少一个真实7日窗口，候选换入、可比数量和缺口原因公开；30日榜必须等真实有效窗口形成后验收。

## 下一阶段：有来源的选型信息

采集并标明许可证原文、安装文档、支持平台与维护证据的链接和时间；资源需求只引用明确文档，缺失显示未知。建立人工纠错、覆盖撤销、失败重试流程。不要用Star数自动推断质量或商业可用性。

在真实规模下测量首次筛选下载量、详情/目录构建时长，再决定紧凑索引、分片和增量构建。RSS已存在；收藏更新提醒、保存搜索及订阅在数据连续性稳定后推进，并尊重用户主动选择。
